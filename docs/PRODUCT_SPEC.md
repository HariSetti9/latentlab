# LATENTLAB Product Specification

## Product sentence

LATENTLAB is a one-minute interactive experiment showing that repeated hidden-state updates can change a prediction without producing a verbal chain of thought - and that extra updates do not guarantee indefinite improvement.

## Learner and prerequisites

The primary learner is an average data scientist or technically curious ML student familiar with vectors, neural-network basics, and Transformers at a high level. Graph algorithms, recurrent networks, and BDH are taught in context rather than assumed.

## Learning objectives

1. Identify recurrent latent computation as repeated updates to internal state.
2. Manipulate update count and connect it to a visible measured consequence.
3. Compare a model estimate with an independently computed answer.
4. Distinguish additional hidden computation from additional generated reasoning tokens.
5. State the analogy and non-equivalence between the toy and BDH-CQ.

## Guided journey

### Stop 1 - Guide: one live question

- Opening question: “Can an AI think longer without talking longer?”
- A small maze is already active at four updates.
- Visible together: maze, current task-relevant state, estimate, BFS truth, correctness, and state delta.
- Learner action: press `1`, `2`, `4`, `8`, or `16` update button or use arrow keys on the update control.
- Consequence: actual recurrence reruns from the same input; changed cells, estimate, delta, and compute count update immediately.

### Stop 2 - Experiment and observe

- Prompt: compare one update with the first update count that reaches the goal.
- Caption is computed from differences: number of newly reached cells, whether the goal estimate changed, and whether the state reached a fixed point.
- No caption claims a semantic hidden thought or produces chain-of-thought.

### Stop 3 - Compare with truth

- BFS truth remains visible and is labeled `INDEPENDENT REFERENCE`.
- Toy output is labeled `LIVE COMPUTATION · TOY MODEL`.
- Learner sees correct/incorrect plus distance error when distance is defined.
- “Why trust the reference?” opens a compact, inspectable BFS explanation and code link.

### Stop 4 - Challenge the claim

- The learner loads a fixed limitation preset selected only after Phase 3 evaluation.
- Preferred honest case: finite-depth underreach followed by saturation. An oscillation/interference preset is shown only if generated by the committed recurrence, never scripted.
- Prompt: “Did more compute help at every step?”
- The explanation distinguishes `changed`, `helped`, and `converged`.

### Stop 5 - Connect to BDH-CQ and explain

- An original three-column comparison contrasts explicit-token reasoning, the toy, and published BDH/BDH-CQ.
- Evidence labels separate developer-reported published mechanisms from our experiment.
- Learner answers three short self-checks and completes: “Extra recurrent steps can ___, but they do not guarantee ___.”

### Sandbox

Only after the guided insight, the learner may edit walls/start/goal, choose a deterministic seed, and set 0-32 updates. Invalid puzzles show an inline explanation and retain the last valid result.

## Metric definitions

- **Updates:** exact number of recurrence applications from the initialized state.
- **Reached cells:** count of non-wall cells marked reachable by the current recurrent state.
- **Goal estimate:** whether/distance at which the recurrence currently marks the goal reachable.
- **Ground truth:** reachability and shortest distance computed by a separate BFS implementation.
- **State delta:** number of grid cells whose task-relevant state changed in the latest update.
- **Compute proxy:** update count multiplied by traversable-cell count; labeled as a deterministic operation proxy, not wall-clock cost or FLOPs.

Confidence will not be displayed unless a legitimate probabilistic model is adopted and calibrated.

## BDH/BDH-CQ integration point

The connection appears immediately after the learner observes repeated internal updates and the failure case. It explains that BDH-CQ's authors describe learned recurrent memory and iterative latent query computation, while the toy has transparent fixed rules, no in-context learning, and no BDH architecture. Detailed allowed wording comes only from `research/CLAIMS_LEDGER.csv`.

## Performance budget

- Interaction-to-paint target: <100 ms on the reference development laptop for 32 updates on a 15x15 grid; public claim only after measurement.
- Initial compressed JS/CSS target: <200 kB excluding sourcemaps.
- No network request is required for the core experiment after initial load.
- Stable layout; no auto-playing essential animation; optional transition duration <=250 ms.

## Accessibility and responsive behavior

- Logical semantic heading order, native buttons/inputs, visible focus, and keyboard-operable grid editing.
- State is expressed by labels/patterns/symbols and a text table, never color alone.
- Screen-reader summary announces update count, prediction, truth, correctness, delta, and convergence.
- `prefers-reduced-motion` disables interpolation and scrolling motion.
- Minimum 44x44 CSS-pixel touch targets for primary controls.
- At <=720 px, truth and estimate remain adjacent in one compact comparison row; the visualization stacks without horizontal page scrolling.

## Privacy and analytics

No login, cookies, analytics, personal-data collection, or remote inference. Self-check answers remain in component memory and are neither persisted nor transmitted.

## Error and loading states

- Default computation is synchronous and available before first meaningful paint.
- Corrupt fixture: show a plain-language error, fall back to a bundled safe preset, and retain source detail for developers.
- Unsupported optional visualization capability: render the semantic HTML/text state view.
- Invalid sandbox: identify the exact invalid field/cell and do not crash or silently coerce.

## Phase 4 implementation note

Implemented as a single-page React explainer with five guided stops, live default depth-sensitive fixture, trace playback, independent-reference comparison, convergence chart, shallow/deeper comparison, computed limitation callout, and a secondary validated 4x4 sandbox. Deterministic screenshot routes accept `fixture` and `depth` query parameters. See `UI_ARCHITECTURE.md` and `ACCESSIBILITY.md`.
